# Pixel 6 FTM5 FIFO: one bounded hardware read

**Observed on hardware, 2026-10-27 PDT:** An isolated Pixel 6 (`oriole`, Android build `CP3A.261005.002.A1`) probe read chip ID `36 48`, then made exactly one FTM5 event-FIFO read. The eight returned bytes were `03 00 00 00 00 00 00 00`. The probe reported `first=OK`, `cleanup=OK`, and restored LDO26M and LDO25M to their original disabled values. The phone returned to authorized Android ADB afterward. The [sanitized capture](../research/pixelios-kernel/device/google/oriole/hardware/touch-fifo-ready-2026-10-27.txt) records the decisive lines. The exact temporary-boot image SHA-256 was `d2ba3c760bbfcbc8deec793c040317c3727fb8ad230112eaa81bbcacf781d990`, built from commit `09f70f5`. No partition was flashed in this test.

**Read from source:** Google's FTM5 protocol defines an eight-byte event and SPI read command `0x87` with a dummy byte before the reply (`ftsHardware.h` and `ftsIO.c` in [`kernel/google-modules/touch/fts_touch`](https://android.googlesource.com/kernel/google-modules/touch/fts_touch/)). Its driver reads the FIFO during the ready-event path. `0x03` is consistent with a controller-ready event after reset. This interpretation is limited to the event header; the remaining zero bytes and a single boot-time sample cannot establish interrupt delivery, finger tracking, or gesture input in XNU.

**Read from this repository:** `shim/build.sh --board oriole --avb --usb-gadget --inventory-touch-fifo` selects a separate probe profile. It performs the previously verified ID exchange, transmits one `0x87` command and reads one dummy plus eight bytes under the same GPIO chip select, then follows the existing restoration path. The host helper requires an explicit `--touch-fifo` selection, the matching image marker, a private exact-image SHA-256 pin, the recorded unlocked Oriole, and the same bootloader/slot/partition geometry baseline. The USB report rejects incomplete captures, invalid event bytes, a missing FIFO marker, or a failed ID/status before claiming a successful FIFO read. It always leaves `ios_touch_or_gestures_verified=false`.

**Verification:** A different-model reviewer checked the hardware writer against the Google FTM5 source and reviewed the host boot gate. Fault-injection tests cover SPI read/write failures and independent cleanup attempts. The full repository gate passed at `09f70f5`; the exact FIFO image was rebuilt *after* that gate, which overwrites `shim/out`. These host checks do not guarantee that hardware restores a register if its write fails; the physical run's readbacks are the evidence for this particular attempt.

**Next development gate:** The XNU touch driver still has no Oriole-owned rail lifecycle. The current iOS ADT profile removes `/sweet-touch`, so no physical touch events reach SpringBoard. Build an opt-in XNU bring-up profile that powers and verifies the two rails, owns SPI11 and reset, identifies `36 48` inside XNU, polls a bounded ready/FIFO read, then reports one-finger down/move/up to the existing HID path. Keep the no-touch profile available and measure physical swipe, tap, app launch, and return Home separately. Do not infer those outcomes from this pre-kernel ready event or from a software-injected Home event. The Android factory reset erased the prior iOS root in `userdata`; another root flash needs a fresh exact-image check and user confirmation immediately before writing.
