# Oriole UFS root timeout: next bounded experiment

## 2026-10-25 PDT: launchd reached mount, RAM-COW candidate

- **Observed on hardware:** the exact read-only platform image SHA-256 42c5f22dea6a6948bc71fbbafa6016fcf59c6594c61571ad00062162b1a208ba passed the earlier wrong-platform failure. The screen shows launchd entering on-demand mode and spawning fsck and mount. Its mount phase reports "mount_hfs: Read-only file system", "mount: / failed with 1", then XNU panics because mount PID 3 exited with status 1. This proves launchd executed; it does not prove SpringBoard or home-screen startup. The user photo is outside Git. The temporary boot made no new partition writes.
- **Read from source:** patch 0105-oriole-ram-cow-root.patch adds an exact Oriole-only RAM block overlay. The ADT must contain both oriole-root-board=oriole and oriole-cow-board=oriole-cow; boot args must include ufscow=1 rootrw=1 while retaining ufsrw=0 sweetlog=0 ufscache=0 ufswait=0. The XNU SCSI allowlist and separate Oriole WRITE(10) guard still forbid physical UFS writes. This makes the virtual root writable only for the current boot; reset discards all changes.
- **Verified offline, not yet observed on hardware:** a byte-reproducible replacement UFS object was built from the exact 0105 patch. The strict PIE relink produced kernel SHA-256 753d090ab2d833b111e8eb54008b4e984c35bf6f6913a7b492c305fe75cc0d5f; the separate profile produced payload SHA-256 bb08d5b9db73b7dd3f263b2b97ec336c7f44e3fd37313a8b622aef17d18d7d3b. An independent review found no remaining physical-write path and verified the source-to-object-to-kernel-to-payload provenance. The full repository gate passed with local macOS cross-toolchain wrappers (GATE PASS b102b6c+dirty). The exact AVB shim image, SHA-256 a2a94f26163a80c8dc6dce75b3b06b7fe8597dd5f0d4dd1a665e44ed05343a23, passed both the payload checker and imgmeta freshness/kind check. It has not yet been started on the phone.
- **Known limitation:** COW pages use nonblocking allocation under the storage mutex and are capped at 65,536 four-kilobyte pages. Allocation may fail before the cap; a single large request can partially complete earlier bounce chunks. A failed or reset boot leaves the underlying no-journal iOS root unchanged.

- **Read from source:** XNU's `bsd/sys/reason.h` maps namespace 9 to `OS_REASON_EXEC` and code 14 (`0xe`) to `EXEC_EXIT_REASON_WRONG_PLATFORM`. In `bsd/kern/kern_exec.c`, the macOS-targeted DEVELOPMENT path refuses an iOS binary without a matching spawn-platform attribute unless `unentitled_ios_sim_launch` or the no-sandbox entitlement is present. The tested Oriole read-only payload omitted `unentitled_ios_sim_launch=1`, although the upstream Sweet image builder includes it. `CS_KILLED` alone does not identify a corrupt signature; the structured exit reason identifies this platform check. This is a source-based diagnosis, not yet a tested fix.

### Next gates toward the iOS home screen

1. **Observed status:** the no-journal HFSX root mounted; the first confirmed failure is `EXEC_EXIT_REASON_WRONG_PLATFORM` when loading launchd. Build and independently review a separate read-only platform-argument profile, then boot it temporarily once the phone is recoverable and capture the next failure or success. The prior 0-byte USB log was insufficient by itself; the screen photo supplied the missing evidence.
2. **Read from source:** the upstream Sweet write patch (`research/pixelios-kernel/xnu/patches/0030-sweet-ufs-writes.patch`) accepts `ufsrw=1`, sends WRITE(10), and uses a whole-LUN SYNCHRONIZE CACHE(10). The root patch (`0031-sweet-read-write-root.patch`) accepts `rootrw=1` and bypasses the dirty non-journaled root check. Those behaviors need an Oriole-only exact opt-in profile, independent review, bounds/overflow and UPIU/UTRD tests, and a fail-closed dirty-root policy before any writable hardware boot. The existing read-only profile must stay unchanged.
3. **Guess to test later:** once a verified writable HFSX root can mount, launchd, dyld, the shared cache, frameworks, SpringBoard, display/input services, and persistent storage still need separate on-device evidence. Reaching a RAM test PID 1 does not establish this chain.

The native `xnu-ufsroot` boot on 2026-10-25 reached XNU and then timed out three times on SCSI TEST UNIT READY (`0x00`), ending at `IOFindBSDRoot: ... ufsroot0 unavailable: 60`. It did not mount a root filesystem or enter iOS userspace. The Pixel 6 was recovered by holding Power; ADB confirmed Android CP3A.261005.002.A1, slot b, bootloader slider-17.0-15681480. The boot used `fastboot boot`; no media was flashed or erased. Evidence is in ignored `private/ufsroot-rsr1-native-evidence/` and `private/ufsroot-rsr1-native-usb1/`.

The only successful hardware command trace so far came from the shim's `INVENTORY_UFS` path. It ran `ufs_cold_init()` first, then started its own UTRL, sent NOP OUT, received one UNIT ATTENTION on TUR, retried TUR successfully, and read capacity/GPT. The native storage-root path is different: the shim only checks existing HCE/DP/CAP/VER/DBR/RSR, and XNU stops/replaces the UTRL, disables UFS interrupts, then sends TUR directly. The preflight proves a quiet, apparently ready host but does not prove the device can complete a command later in XNU. The cold init, NOP, interrupt-enable state, time elapsed, and XNU DMA/cache mapping are therefore unresolved differences; none is yet established as the cause.

Next candidate: add a dedicated *temporary-boot-only* ready-host shim diagnostic that uses the exact CP3A board/firmware and DMA-placement guards, does not cold-init, and attempts only NOP OUT, TUR, and optionally READ CAPACITY(10). Log HCE/HCS/IS/IE/UECPA/RSR/DBR/UTRLBA/U at admission, after list start, before first doorbell, and at bounded timeout. Preserve the already reviewed ownership rules: DBR must be zero before replacing a foreign list; clear only a request slot owned by this diagnostic; stop the owned list within a bound; reset directly on uncertain ownership. No media writes or partition writes. Screen/USB logs should survive long enough to capture both success and failure. A first failure must not proceed into XNU.

Interpretation: if the ready-host shim command also times out, investigate link/clock/power state and the need for cold initialization before modifying XNU. If it succeeds, instrument XNU's first TUR with the same MMIO snapshots and descriptor address/OCS data; compare before adding a NOP or changing interrupt/cache behavior. Change one difference per run. A command timeout should remain a failed diagnostic, never trigger a userdata flash.

Before hardware: source review, host fake-register/timeout tests, exact image/payload hashes, full repository gate, and a serial-specific check of product/firmware/slot/bootloader. The native `xnu-ufsroot` mode remains disabled in the private boot baseline until a new candidate passes this gate. `fastboot boot` only; verify fully booted Android and unchanged CP3A/slot b after each trial.
