# Oriole UFS root timeout: next bounded experiment

The native `xnu-ufsroot` boot on 2026-10-25 reached XNU and then timed out three times on SCSI TEST UNIT READY (`0x00`), ending at `IOFindBSDRoot: ... ufsroot0 unavailable: 60`. It did not mount a root filesystem or enter iOS userspace. The Pixel 6 was recovered by holding Power; ADB confirmed Android CP3A.261005.002.A1, slot b, bootloader slider-17.0-15681480. The boot used `fastboot boot`; no media was flashed or erased. Evidence is in ignored `private/ufsroot-rsr1-native-evidence/` and `private/ufsroot-rsr1-native-usb1/`.

The only successful hardware command trace so far came from the shim's `INVENTORY_UFS` path. It ran `ufs_cold_init()` first, then started its own UTRL, sent NOP OUT, received one UNIT ATTENTION on TUR, retried TUR successfully, and read capacity/GPT. The native storage-root path is different: the shim only checks existing HCE/DP/CAP/VER/DBR/RSR, and XNU stops/replaces the UTRL, disables UFS interrupts, then sends TUR directly. The preflight proves a quiet, apparently ready host but does not prove the device can complete a command later in XNU. The cold init, NOP, interrupt-enable state, time elapsed, and XNU DMA/cache mapping are therefore unresolved differences; none is yet established as the cause.

Next candidate: add a dedicated *temporary-boot-only* ready-host shim diagnostic that uses the exact CP3A board/firmware and DMA-placement guards, does not cold-init, and attempts only NOP OUT, TUR, and optionally READ CAPACITY(10). Log HCE/HCS/IS/IE/UECPA/RSR/DBR/UTRLBA/U at admission, after list start, before first doorbell, and at bounded timeout. Preserve the already reviewed ownership rules: DBR must be zero before replacing a foreign list; clear only a request slot owned by this diagnostic; stop the owned list within a bound; reset directly on uncertain ownership. No media writes or partition writes. Screen/USB logs should survive long enough to capture both success and failure. A first failure must not proceed into XNU.

Interpretation: if the ready-host shim command also times out, investigate link/clock/power state and the need for cold initialization before modifying XNU. If it succeeds, instrument XNU's first TUR with the same MMIO snapshots and descriptor address/OCS data; compare before adding a NOP or changing interrupt/cache behavior. Change one difference per run. A command timeout should remain a failed diagnostic, never trigger a userdata flash.

Before hardware: source review, host fake-register/timeout tests, exact image/payload hashes, full repository gate, and a serial-specific check of product/firmware/slot/bootloader. The native `xnu-ufsroot` mode remains disabled in the private boot baseline until a new candidate passes this gate. `fastboot boot` only; verify fully booted Android and unchanged CP3A/slot b after each trial.
