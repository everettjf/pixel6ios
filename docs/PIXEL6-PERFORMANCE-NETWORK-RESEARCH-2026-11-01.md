# Pixel 6 performance and networking: research handoff

**November 1, 2026. Research only; no implementation is planned.** This note compares public XNU-on-Android ports with the observed Pixel 6 (`oriole`) result. It records directions to investigate if the project is ever resumed. It does not change the boot image, root volume, device configuration, or installation status.

## What is established on this Pixel 6

- **Observed on hardware:** iOS 16.7.16 reached the lock screen and Home Screen, accepted physical touch, opened apps, and navigated through Settings. Interaction was extremely slow. These observations are from one experimental device and are not a benchmark; see [Milestone 1](MILESTONE-ONE.md).
- **Read from the tested configuration:** the recorded Home Screen boot used `cpus=1` and a CPU-driven framebuffer path. The [framebuffer patch](../research/pixelios-kernel/xnu/patches/0056-sweet-fb-throttled-present.patch) says a 10 MB copy on every 60 Hz swap occupied the CPU, so it defaults to presenting the latest frame at 10 Hz (`sweetfb_hz`). See the [boot arguments](PIXEL6-IOS-HOMESCREEN.md). The exact share of delay due to CPU count, clocks, software composition, panel copy, storage, and logging has **not** been measured on the final interactive build. There is no verified Pixel 6 GUI GPU acceleration.
- **Observed on hardware:** USB ECM carried local IP traffic: the Mac received ICMP replies from the phone after iOS `configd` started. No phone-originated public HTTP response, DNS answer, or successful Safari page load has been recorded. The host did not apply scoped NAT, DHCP, or DNS during that trial. See the [October 29 network record](PIXEL6-NETWORK-TRIAL-2026-10-29.md).
- **Read from the root image and source:** the inspected root preferences lack a USB `NetworkServices`/IPv4/DNS entry. The kernel-created `ue0` does not by itself prove that iOS publishes an `IONetworkInterface` service or accepts it as a usable network service. The logged `configd` route deletions are requests, not proof of the final route table; see [USB Internet research](PIXEL6-USB-INTERNET.md).

### Performance direction, if work resumes

1. **Measure before changing policy.** On the same pinned image, collect touch-event-to-display latency, frame swaps and actual presentations, CPU busy time by thread, panel-copy duration, boot-time clocks, UFS waits, and log volume. Record a short repeatable interaction and the exact image hash. This distinguishes input delay from rendering and display delay.
2. **Qualify CPU and display separately.** The known baseline is one CPU and a default 10 Hz presentation cap. A higher cap alone can recreate the 10 MB-per-swap CPU saturation noted in our patch. Any multi-core or clock change needs GS101-specific interrupt, coherency, power, and thermal evidence; the Qualcomm `cpufreq` code is not reusable. Compare measured latency and temperature after each isolated change.
3. **Reduce panel-copy cost before promising smoothness.** `ios-topaz` demonstrates direct display scanout from suitable contiguous surfaces. On Oriole, the equivalent design would have to establish the actual Samsung display/RDMA scanout contract, addressability, surface lifetime, cache and S2MPU/IOMMU behavior, and safe fallback. This is a research hypothesis, not an approved patch or known Pixel 6 hardware path. The present [GS101 GPU notes](../research/pixelios-kernel/soc/google/gs101/soc.json) identify Mali-G78; bringing that GPU to iOS composition is a separate, substantially larger project.

**Performance acceptance if revisited:** a logged, repeatable comparison on the same phone that reports median and tail touch-to-visible-frame latency, delivered frame intervals, CPU utilization, temperature, and stability. Do not infer 60 fps from a boot argument or from another device's video.

### Network direction, if work resumes

1. **Prove phone-to-host application TCP first.** The existing [local HTTP probe](../tools/probe_oriole_usb_http.py) serves a random URL on the Mac's USB address. A matching Safari request would isolate the local `ue0`/USB/TCP/app path without external routing or DNS. Timeout alone does not locate the failure.
2. **Inspect actual iOS network state.** Capture the device's live interface address, route table, network-service registration, and resolver selection after `configd` settles. The `ios-sweet` plist experiment is evidence that writing a guessed service entry alone may fail. Determine whether the missing link is an IOKit `IONetworkInterface`, service preferences, route ownership, or an app-level request.
3. **Only then test external transit.** The existing [scoped host plan](PIXEL6-NETWORK-TRIAL-2026-10-29.md#scoped-host-preparation) has syntax-checked DHCP, DNS, and NAT templates but has never been applied. After confirming the exact USB interface and uplink, verify in order: phone-to-host TCP, public-IP request with host forwarding/NAT counters, phone DNS query and answer, then a rendered Safari page. Preserve packet captures or counters for each claim.
4. **Treat Wi-Fi as a separate port.** `ios-topaz`, `ios-apollo`, HakiOS, and UniXNU use Qualcomm radio and transport stacks. This repository's [GS101 hardware inventory](../research/pixelios-kernel/soc/google/gs101/soc.json) identifies a BCM4389 path. Wi-Fi would need Pixel-specific PCIe, firmware, radio, and iOS network-interface work; it is not required to diagnose the existing USB path.

**Network acceptance if revisited:** a phone-originated external response and DNS answer correlated with a successful page in Safari, with the exact image, network configuration, and device state recorded. A Mac ping reply or a running `mDNSResponder` alone does not meet this gate.

## Disposition

The project's [archive status](ARCHIVE-STATE.md) remains in force. This note is a source-backed handoff for possible future work, not a development commitment, tested fix, new installation procedure, or claim that external ports run on Pixel 6. No upstream code or Apple binaries were imported.
