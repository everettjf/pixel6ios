# Oriole touch ID probe: implementation gate

Status: work in progress on `wip/oriole-touch-id-hw`, 2026-10-26 PDT. An isolated `--inventory-touch-id` image passed the full gate and independent hardware-writer review, then made four bounded physical runs on Pixel 6. All four stopped **before sending an SPI ID command** and restored both touch rails exactly. The first found `USI_OPTION=1`; the second found the additional handoff value `USI_CON=1`. The third accepted both values but failed in SPI preparation, and its engine cleanup reported an error. The fourth identified the failed preparation operation and a cleanup mismatch. Therefore full register restoration is **unverified**. A source-backed, independently reviewed correction is built but has **not** run on hardware. No touch driver, gesture, or app-opening result exists from this probe.

The first independent review identified missing live-FDT/RAM gates and incomplete restoration around USI reset. The candidate now requires the live root compatible token `google,GS101 Oriole` and a live `/memory` range containing the image, and refuses a non-default SPI engine before reset. It also marks all captured engine fields for restoration before reset and checks the untouched engine words remain zero. Host tests exercise these failures and a reset that clears fake SPI registers. The second review found incomplete store provenance and fault injection; the repair uses the existing control-flow-sensitive object store auditor and tests a post-application write error and read faults. These host checks do **not** prove real reset semantics. Google's [Oriole device-tree overlay](https://android.googlesource.com/kernel/devices/google/raviole/+/refs/tags/android-16.0.0_r0.9/dts/gs101-oriole.dts) is the source for the compatible string.

The candidate combines two source paths deliberately: Linux's Oriole probe supplies rail order and a 10 ms active-low reset pulse; the ABL manual-burst sequence supplies the USI/SPI setup and `FB 20` command. ABL writes `USI_OPTION` bit 0, while the Linux controller code uses bit 1. This profile now uses **bit 0**, matching the manual-burst sequence; no source proves the two bits interchangeable. It waits a bounded 100 ms after releasing reset before its single ID attempt. This is a conservative settling interval, **not** a verified ready signal: Linux instead polls the controller-ready event, and a timeout or incorrect ID must be treated as a failed experiment. The first live SPI attempt is intended to measure this assumption, not establish a functional touch driver.

**Observed on hardware, first run:** The [sanitized capture](../research/pixelios-kernel/device/google/oriole/hardware/touch-id-refusal-2026-10-26.txt) records initial LDO25M/LDO26M values `0x2c`/`0x3c`, enabled values `0xac`/`0xbc`, and exact reverse readbacks to `0x3c`/`0x2c`. The SPI-engine gate stopped at PA `0x10D400C4` (`USI_OPTION`) with `0x1`; attempts remained zero. The remaining SPI engine values were not emitted by that image. The revised gate accepts only this source-backed, measured `USI_OPTION=1` and continues to refuse any other non-default engine word, logging all of them before deciding. The revision still requires its own full gate, independent review, exact image pin, and new physical capture.

**Observed on hardware, second run:** The [sanitized engine capture](../research/pixelios-kernel/device/google/oriole/hardware/touch-id-engine-refusal-2026-10-26.txt) records `USI_OPTION=1`, `USI_CON=1`, `CS_REG=1`, and zero for the seven other captured engine words. It again restored LDO26M then LDO25M to `0x3c` and `0x2c`, with zero SPI attempts. The code's USI_CON expectation was the only mismatch. *Read from source:* ABL's manual-burst initialization asserts bit 0 of USI_CON and later clears it; Linux's USI driver releases an asserted reset. The candidate therefore accepts exactly `USI_CON=1` at this handoff and attempts to restore its original value after the one-shot experiment. The third run below showed that the cleanup path still needs diagnosis.

**Observed on hardware, third run:** Commit `ecab7bc` passed the full gate and independent review. Its [sanitized capture](../research/pixelios-kernel/device/google/oriole/hardware/touch-id-prepare-failure-2026-10-26.txt) reports `first=0x0A` (`SPI_PREPARE`), `cleanup=0x0D` (`ENGINE_RESTORE`), zero ID attempts, and both PMIC rails read back at their original disabled values. The image did not log the failing individual operation or final engine words, so the SPI/USI restoration cannot be claimed. The earlier host test passed but did not model the real failure. A more precise, bounded diagnostic and an updated host model need independent review before another hardware-writing test.

**Read from this repository:** The later `e7c26b9` image adds a numbered failure step and individual readback diagnostics without expanding the write set; a different-model reviewer approved one bounded measurement, and the `58617ee` full gate passed. Run `python3 tools/report_touch_id.py private/touch-id-inventory/<capture>/usb.log --out private/touch-id-report.json` from the root checkout to distinguish a complete failed run from a verified `36 48` chip ID. The report always leaves iOS touch and gestures unverified; those need separate XNU and SpringBoard evidence.

**Observed on hardware, fourth run:** Image `b167147` (SHA-256 `0046b45d74eed7d93e14d19eeb7d144a8f81f2a9e496632a995040ceeb2877fd`) was temporarily booted after product, unlock state and firmware baseline checks. Its [sanitized capture](../research/pixelios-kernel/device/google/oriole/hardware/touch-id-step1-failure-2026-10-26.txt) reports `SPI_PREPARE` step 1: GPP23 `DAT` at `0x10c40064` read back `0x30` after a write expecting `0x38` (CS bit 3 high). Cleanup also tried `CH_CFG.SW_RST` (`0x20`) at `0x10d40000`, which read back `0x00`; therefore `ENGINE_RESTORE` failed. No ID attempt occurred. LDO26M and LDO25M read back at their original disabled values. The observed DAT readback does not establish whether the output latch accepted the write while the pin remained configured as an input; the observed SW_RST readback does not distinguish a self-clearing bit from an ignored write. Both require source-backed interpretation and a host test before modifying the writer or running it again.

**Read from source; candidate not yet run on hardware:** [Samsung's GPIO direction-output implementation](https://android.googlesource.com/kernel/common/+/36a279686bc02d340eb213a9f2a0b67e50de64b4/drivers/pinctrl/pinctrl-samsung.c) writes `DAT` before changing `CON` to output. The candidate keeps that order but verifies CS high only after `CON` reports output; if that verification fails, it does not write the SPI/USI engine or transmit an ID command. Cleanup skips engine reset when no engine write was armed, and returns GPIOs to input before restoring their old low `DAT` bits. A failed `CON` restoration suppresses the corresponding low `DAT` write. The host model reproduces the observed input readback (`0x30`), tests a silently ignored CS prewrite and injected read/write failures, and asserts zero engine writes on the ignored-prewrite path. Independent review approved **one bounded diagnostic**; it did not establish that the CS latch accepted the prewrite or that the real GPIO cleanup works. A new temporary-boot capture is required before any claim of progress past step 1.

**Read from this repository; host-only verification:** The root checkout now exposes `tools/run_touch_inventory.py --touch-id --seconds 180`. It requires exactly the recorded Pixel 6 in Fastboot, arms a private USB log before invoking `tools/boot_inventory.py --touch-id`, and selects `tools/report_touch_id.py` rather than the read-only inventory reporter. The boot helper requires an explicit `inventory-touch-id` entry and `inventory_touch_id_image_sha256` in the private firmware baseline, checks the exact image marker, product, unlock state, slot and bootloader, and issues only a temporary `fastboot boot`. Its negative paths and routing were independently reviewed with mocked host execution; this does not verify a phone run. The image-building job must be stopped during the boot so the validated image path cannot be replaced between hashing and fastboot use. Never use the read-only `--touch` selection for the writer image.

**Guess, now partly ruled out:** A host-only fault model at `daba831` simulates SPI `FB_CLK` and `CH_CFG` writes being acknowledged but ignored while `USI_CON.RESET=1`. It reproduces the third run's `SPI_PREPARE`/`ENGINE_RESTORE` stage pair; `800dd0f` pins its more specific simulated signature to prepare step 8, a `FB_CLK` readback mismatch and a later `CH_CFG` mismatch. The fourth run instead failed at step 1, before that model's `FB_CLK` step; the model is not an explanation of this run. [Google's GS SPI driver](https://android.googlesource.com/kernel/google-modules/soc/gs/+/204078758737776959ecc85c527a00fd2cabb62f/drivers/spi/spi-s3c64xx.c) explicitly sets `CH_CFG.SW_RST` and later clears it in `flush_fifo()` (lines 262–303); that source does not establish an automatically clearing reset bit. The full gate passed at `e77d6f7`; the quick-gate selector was also fixed there to include the current Oriole hardware host test from this nested checkout.

## Evidence and target

- **Observed on Pixel 6:** Android exposes `fts` at `spi11.0` and reports a 1080×2400 input range ([sanitized capture](../research/pixelios-kernel/device/google/oriole/hardware/android-touch-2026-10-26.txt)). A shim inventory found USI11 mode 0 and the SPI, mux and reset pads in function 0 at the bootloader handoff ([capture](../research/pixelios-kernel/device/google/oriole/hardware/touch-inventory-2026-10-26.txt)).
- **Observed on Pixel 6:** ACPM reads returned LDO25M `0x2c` and LDO26M `0x3c`, both disabled. A separate bounded image enabled them in that order, read back `0xac` and `0xbc`, then restored LDO26M and LDO25M to their exact initial values ([capture](../research/pixelios-kernel/device/google/oriole/hardware/acpm-touch-rail-cycle-2026-10-26.txt)).
- **Read from source:** Google's GS101 touch device tree maps those LDOs to the FTM5 supplies and maps the controller to SPI11. Its FTM5 probe enables `vdd` then `avdd`, drives reset low for 10 ms and then high. See the pinned links in [PIXEL6-TOUCH-BRINGUP.md](PIXEL6-TOUCH-BRINGUP.md).
- **Read from source:** the existing Bluejay `touchprobe.c` implements ABL-style manual CS, USI mode, clock, pads, reset and the `FB 20 00 00 00` chip-ID request. It is not an Oriole image: `build.sh` currently refuses an Oriole `run` profile. On Bluejay, the SPI engine stalled in earlier experiments; the full writer sequence has not been proved on Oriole ([research 21](../research/pixelios-kernel/docs/research/21-touch-spi-stall-investigation.md)).

The next evidence needed is a bounded SPI response with the expected `36 48` ID (or a precise failure trace). An Android input device alone does not establish that XNU can talk to the controller.

## Proposed isolated image

Use a **new, explicit Oriole inventory profile**, separate from `--inventory-acpm-rail-cycle` and `--touch-probe=run`. Link only the code required for ACPM, USB logging, USI11/SPI11, and the touch pads. No payload, XNU, UFS, userdata access, or generic register poke belongs in this image. Keep the existing Oriole guard; a new allowlist and source/object audit must recognize this profile specifically.

The bounded run should:

1. Validate the same live FDT, RAM, ACPM channel, empty queues, rail registers and exact disabled values as the successful rail-cycle image. Refuse with zero **rail-update, SPI, pad and clock writes** on a mismatch. ACPM `FUNC_READ` itself writes the transport SRAM and mailbox, so a literal zero-MMIO-write claim would be false; its existing bounded transport audit still applies.
2. Snapshot all readable shared state that the SPI probe will modify before the first write: the AP/AOC mux GPIO, four SPI pads, reset GPIO, USI11 mode, CMU_TOP gate, USI11 CMU mux/divider and gates. Do not read USI/SPI engine registers until the USI mode is SPI. Log each snapshot and abort before writing if one fails.
3. Enable LDO25M then LDO26M via the existing gated ACPM client and verify both readbacks. Track publication of *each* request, including uncertain replies, so every possibly enabled rail receives a reverse-order restore attempt.
4. Configure only the source-backed ABL/Linux SPI11 path: AP bus ownership, bounded CMU mux/divider waits at a rate no greater than the device-tree limit, USI SPI mode, pad functions, manual CS and one controller reset pulse. Use the existing five-byte FTM5 hardware-register request. Cap all polls and log the exact first failure.
5. Stop after one chip-ID read or one bounded timeout. Do not scan addresses, retry indefinitely, or start an iOS payload.
6. In a single cleanup path, disable TX/RX, deassert CS, restore reset/pads/mux/CMU/USI fields in reverse dependency order, then restore LDO26M and LDO25M. Read back all restorable fields and both rails. If any restoration is uncertain, emit an explicit failure and never report success. A device reset remains the final containment step.

The existing `touch_probe_run()` is **not** directly callable for this profile: several early returns skip restoration, and it retains mux/clock changes after some transfers. Reuse only individually audited mechanisms or add an independently tested cleanup path. In particular, no SPI register snapshot may be taken while USI mode is 0.

## Review and acceptance

Before hardware: fake-MMIO/APM tests must cover an initial-state mismatch, failed snapshot, published update with a missing reply, each SPI timeout, cleanup after every failure stage, and a failed restore. The source and object audit must prove every MMIO store goes through a profile-specific allowlist and every ACPM update is one of the two bit-7 rail changes. `tools/check-all.sh` must pass, then build the exact Oriole image **after** the gate because the gate overwrites `shim/out/`. A different model family must independently review the hardware writer before it leaves a local `wip/*` branch.

For a real run: verify exactly one fastboot target reports `product: oriole` and an unlocked bootloader; pin the exact image SHA-256 in the private baseline; arm USB capture before `fastboot boot`. Accept the capture only if the full boot marker, ID bytes, bounded cleanup and two exact rail restorations are present. A partial log or timeout is a failed test. Keep serials and raw logs out of Git.

Only after this measurement should an iOS boot profile power the rails for the lifetime of the XNU touch driver, retain a no-touch fallback, and test a physical lock-screen swipe and app tap. The current Android reset erased the prior iOS root in `userdata`; any reflash requires a separate exact-image verification and user confirmation immediately before it.
